# Shopper, security review of 0.1.0

The review of task 12.2 ([`docs/epics/release.md`](../epics/release.md)): what [`DESIGN.md`](../../DESIGN.md) §21 and the rules of [`AGENTS.md`](../../AGENTS.md)
promise, tried against the running, built app and not the code alone, what was found, what was done, and what was left. It is a record of one review at one time
(11 November 2026), in the manner of Tusk's (`sovereignfs/tusk`, `docs/security-review-phase-1.md`). The promises themselves stay in the design. Each protection that
holds is a test, and each test named here that guards a fix was seen to fail with the protection switched off.

**Who did it:** one reviewer, who wrote the code, with the tests and the app. That is a limit, and it is the first thing under _Not done_. Nothing here is an audit.

## Summary

**One thing was found that mattered, and was fixed:** any member of a household could put another member's name on what they added or ticked, because the server checked that
the person named was _in the household_ and not that it was the sender (finding 1). **Two things were found that are not fixed in code and need the owner's decision**
(findings 2 and 3), and one dependency advisory that does not reach what runs (finding 4). **A statement in the first draft of the README was wrong and is corrected:** it
said people's names and addresses are sealed, and the sign-in database holds each account's name and address in plain text (finding 2). Nothing was found open in access
between households, the invitation, sign-in through core and its notices, deletion, caching, redirects or the size of a request. What had been tried by hand is now a
browser test (`e2e/security.spec.ts`), and the rest are listed under _What holds_.

## What was found

### 1. Who added an item, and who ticked it, was whatever the sender said

A change to an item carries `addedBy` and `boughtBy`, and the screens show them as fact ("added by Ada", "ticked by Grace"). `checkReferences` (`src/sync/apply.ts`) asked
that the person be one the household has had, which is right for a reference and wrong for an author: with a second account in the household, one request
`{ table: 'item', id, fields: { boughtAt, boughtBy: <the other member's person id> } }` was **applied**, and so was an item created with `addedBy` set to someone else.
Found by the probe of what a Member can do beyond what the screens offer. Nobody was harmed by it (every member may edit everything), but a household's record of who bought
what was not something its members could rely on, and it is the kind of thing that ends an argument in the wrong direction.

**Fixed:** `checkAuthorship` runs on each change as the device sent it, before it is applied, and refuses (as not found) a change whose `addedBy` or `boughtBy` is not
the sender's own person in that household. It does not run on what the server itself writes when it folds two rows into one, which keeps the earlier adder. Tested at
the data layer on whichever database the leg runs (`src/sync/authorship.test.ts`: the sender accepted as adder and as ticker; another member refused for each, with
nothing written and the item left open; a person who is not in the household refused as before; a fold still keeps the earlier adder) and in the browser
(`e2e/security.spec.ts`). The first two refusals were seen to fail without the fix.

### 2. The sign-in database is not sealed, and the README said it was

Everything that says what a household buys is sealed in the app's database, and a read of its file shows none of it (see _What holds_). **The sign-in database
(`shopper_auth`, better-auth's) holds each account's name and email address in plain text:** a search of its write-ahead log for the addresses and names of two test accounts
found them, and found nothing of what they had bought anywhere. Signing in looks an account up by its address, which a sealed value cannot be. The `person` record in the
app's database, which is what shared rows point at, **is** sealed. The design's table (§13.1) lists `person: name, email` as sealed, which is true of that record; the README
(12.3) went further and said "people's names and addresses", which was not.

**Done:** the README, `docs/encryption.md` and `DESIGN.md` §13.1 now say it, and that encryption at rest protects what a household buys and where, and does not hide who has an
account. **For the owner:** this is a limit of the sign-in library and of how people are found at sign-in, not a bug. It can stay as it is, said plainly (what is done), or a
later release can keep a keyed hash of the address for the lookup and seal the rest, at the cost of replacing how better-auth finds an account. **Accepted by the owner:** not yet.

### 3. The limits count by an address the client can choose

Sign-in (better-auth's own limiter) and opening an invitation link (`app/invite/[token]/page.tsx`, 60 in ten minutes) count by the first value of `X-Forwarded-For`. Behind a
proxy that **replaces** the header with the real connection's address, as Caddy does by default, that is right. With the app reachable directly, or behind one that appends to
what the client sent, a client can send a different value each time and is never limited: tried, 70 requests with 70 different values were all answered, and the same
address was limited after 60. Guessing a link is not made feasible by this (a token is 256 bits), and the accept route is counted by account and not by address, but sign-in
guessing and a flood of rows in the counter table are.

**Done:** the README and `deploy/README.md` say that the proxy must set `X-Forwarded-For` from the real connection and replace any the client sent, with nginx's line.
**For the owner:** whether that is enough, or the image should take the address from the connection when it is not told to trust a proxy (a setting, as
`SHOPPER_TRUST_PROXY`), which changes how a hosted instance is configured. **Accepted by the owner:** not yet.

### 4. A dependency advisory in a build tool

`pnpm audit --prod` reports one moderate advisory (GHSA-67mh-4wv8-2f99): `esbuild` up to 0.24.2 lets a website send requests to **its development server**, reached through
`better-auth` to `drizzle-kit` to `@esbuild-kit`. The standalone server the image runs contains neither `esbuild` nor `drizzle-kit`, and nothing here starts esbuild's dev
server, so it does not reach a running Shopper. It waits for a better-auth release that drops the old loader. **Accepted by the owner:** not yet.

## What holds

Each is a test, or a probe made with two real accounts against the built app and now a browser test (`e2e/security.spec.ts`).

**Access (§5.2).** A person who is not in a household cannot write to it, make an item that points at its list from their own, or ask what changed in it (they are told it is
gone), and every refusal for another person's household reads the same as for one that does not exist. Every operation of `/api/ops` is a second-person test (not found for an
outsider; a Member's attempt to remove the Admin, to revoke another's link or to make an Admin's call, the same). `src/access/routes.ts` lists every page and route and is
held to `app/`. A client cannot set `seq`, a field stamp or a `householdId`. A Member is given no other member's address, and an Admin is given a member's.

**Every route that changes something** refuses a request with no `Origin`, with another site's and with `null`: sync, operations, accepting a link, the profile and deleting
the account. The session cookie is `HttpOnly`, `SameSite=Lax`, prefixed `shopper`, and `Secure` under https.

**What is a person's is not cached.** Every signed-in page and every API answer carries `no-store`; so does the invitation page (which has a token in its address) and the
sign-in pages. The service worker keeps only an allow-list (the build's files, icons and the one shell page, which holds nothing of a person) and the browser tests look into its
caches after a tour and after sign-out. Every page has a nonce policy with no `unsafe-inline` or `eval` for scripts, `frame-ancestors 'none'`, `nosniff` and
`Referrer-Policy: no-referrer`, so a token in an address is not sent on. Nothing third-party loads; what people write is rendered as text (no `innerHTML` sink exists in
`src/` or `app/` but the nonce'd theme script).

**Sync and folding (§12.4, §12.5).** A mutation is applied in one transaction that steps the household's counter in the statement that proves membership; a replay writes nothing;
a row that is another household's reads as not found; a request is bounded (200 mutations, 2 MB, both tried at ten times the limit). Folding is by household, aliases are looked up
by household, and the property tests of random interleavings from several devices hold. Finding 1 is the one place this was found short.

**Sealing and the name key (§13).** A search of the app database's file and its write-ahead log for the names of a household, its lists, items and products found nothing; a
test holds `sealed.ts` to the design's table, rotation re-wraps every row and recomputes every name key, and start-up stops when sealed content cannot be opened with the keys given. The name key
is keyed per household. Finding 2 is what is _not_ sealed.

**Invitations (§7.3).** A token is 32 random bytes; only its SHA-256 is stored and it is compared in constant time; it is claimed in the transaction that adds the member, so it cannot
be used twice; every link that does not work shows one page; revoking is by the maker or an Admin in the statement; at most 20 are live; opening and accepting are counted (finding 3
for the first); a person who leaves or is deleted has their links revoked. The page shows the household's name and the inviter's, and nothing else.

**Sign-in through core and its notices (§15).** A core login whose address is a local account's is refused and makes and touches nothing; a core account is made whatever sign-up says;
nothing is linked by address; tokens from core are kept encrypted. The two notices are checked by the SDK (signature, issuer, audience, age, event, `jti`), refuse a replay even to a
process that has just started, read a bounded form, are rate limited before core is asked anything, are never cached and are 404 where core is not set. Sign-in will not send
anyone to another site: `https://`, `//`, `/\` and `javascript:` addresses are refused (`e2e/security.spec.ts`), and `?next=` follows only an invitation's page.

**Deletion (§19).** A test decides what happens to every table (it fails for a new table that is not decided), seeds one row of each, and finds nothing personal left; the Admin role
passes on and shared households go on whole; running it twice is safe; after deleting, the session is refused at once (401) and the sign-in is gone. A core account's deletion by notice
does the same.

**Logs** hold ids and kinds of failure: the server's log after the probes, with eight accounts' worth of names, notes and addresses sent through it, held none of them.

## Not done

- **An independent review.** This was the author's, with the author's blind spots. An outside review before the first release is the thing most worth the owner's time and money.
- **WebKit, a real phone, PostgreSQL and sqld.** The browser tests ran in Chromium and the data-layer tests on a SQLite file here; CI runs the other forms.
- **A penetration test, fuzzing and load.** Nothing was fuzzed beyond the size and shape of a request, and nothing was tried under load.
- **A real core.** Sign-in and the notices were tried against the fake Sovereign and the SDK's fake core, which are held to a recorded discovery document, not a live instance.
- **The supply chain beyond `pnpm audit`.** The lockfile is frozen, installs refuse a release less than a day old, and install scripts are off, but the packages were not read.
- **The surfaces of later phases:** the live stream, import, the directory and mail are reviewed with the phase that adds them.
