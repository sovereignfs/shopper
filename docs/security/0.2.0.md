# Security review: 0.2.0 (workstream 0001)

**Date:** 2026-11-21 · **Scope:** what workstream 0001 added to 0.1.0 (RFC 0001 to 0003): sign-in that never sends a password, Shopper's vault and core's key
release, households encrypted by their devices, links that carry keys, Web Push, core's export of a person. **By:** Claude Code, at the owner's request;
not an independent review, and **not an audit**: the suite's encryption it builds on is not yet audited either (`sovereign`'s RFC 0005).

## Findings

1. **A shared household is still sealed by the server** (RFC 0001 amendment 2): its content is as readable to whoever runs the server as in 0.1.0. Said in
   Settings and `docs/encryption.md`; ends with 16.8 and 18.8. **Accepted, documented.**
2. **Removing a member does not change a household's keys** (18.8). A removed member no longer receives anything; one who kept the keys and also had a copy
   of the database could read what is added after. Said in `docs/encryption.md`. **Accepted, documented.**
3. **The keyring and link wraps are Shopper's own use of WebCrypto's AES-GCM** (16.9, 16.15), not an SDK call: a random 12-byte nonce per wrap, the
   person or link and household bound as associated data. Small, but the one piece of cryptography Shopper writes. **To move onto the SDK when it can.**
4. **A 0.1.0 password is sent to the server once more,** when its account moves across. It was sent at every sign-in before; it is the last time.
   **Accepted.**
5. **A link that leaks before it is used gives its household's keys** to whoever uses it first, as it gives membership. The dialog says to send it
   privately, and revoking it deletes the wrapped copy. **Accepted, as the design says.**
6. **The replay memory of core's export requests is per process.** An export asked for twice is the same export, so a replay does no harm. **Accepted.**

## Not covered

A push received in a real browser; core's key release end to end (the SDK's fake core has none, 16.16); WebKit; a restore from a backup run by hand.
