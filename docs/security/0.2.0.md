# Security review: 0.2.0 (workstream 0001)

**Date:** 2026-11-21 · **Scope:** what workstream 0001 added to 0.1.0 (RFC 0001 to 0003): sign-in that never sends a password, Shopper's vault and core's key
release, households encrypted by their devices, links that carry keys, Web Push, core's export of a person. **By:** Claude Code, at the owner's request;
not an independent review, and **not an audit**: the suite's encryption it builds on is not yet audited either (`sovereign`'s RFC 0005).

## What was checked

| Area                      | What                                                                                                                                              | Held by                                                                                 |
| ------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------- |
| No password to the server | Every route that took one refuses anything but a derived value; the one exception, moving a 0.1.0 password once, is rate limited and says nothing | `src/auth/auth.test.ts` (seen to fail with the hook off), `vault.test.ts`               |

| Binding                   | A value opens only under its household, table, row and field, or a row folded into it; a keyring only for its person and household                | `src/keys/household.test.ts`, `transport.test.ts`                                       |
| Holding                   | A mutation in the wrong form is held only after membership and authorship are checked, so it says nothing to an outsider                          | `e2e/security.spec.ts`, `src/sync/encrypted.test.ts`                                    |

## Findings

1. **A shared household is still sealed by the server** (RFC 0001 amendment 2): its content is as readable to whoever runs the server as in 0.1.0. Said in
   Settings and `docs/encryption.md`; ends with 16.8 and 18.8. **Accepted, documented.**
2. **Removing a member does not change a household's keys** (18.8). A removed member no longer receives anything; one who kept the keys and also had a copy
   of the database could read what is added after. Said in `docs/encryption.md`. **Accepted, documented.**
3. **The keyring and link wraps are Shopper's own use of WebCrypto's AES-GCM** (16.9, 16.15), not an SDK call: a random 12-byte nonce per wrap, the
   person or link and household bound as associated data. Small, but the one piece of cryptography Shopper writes. **To move onto the SDK when it can.**
4. **A 0.1.0 password is sent to the server once more,** when its account moves across. It was sent at every sign-in before; it is the last time.
   **Accepted.**
5. **A link that leaks before it is used gives its household's keys** to whoever uses it first, as it gives membership. The dialog says to send it
   privately, and revoking it deletes the wrapped copy. **Accepted, as the design says.**
6. **The replay memory of core's export requests is per process.** An export asked for twice is the same export, so a replay does no harm. **Accepted.**

## Not covered

A push received in a real browser; core's key release end to end (the SDK's fake core has none, 16.16); WebKit; a restore from a backup run by hand.

## Addendum: lists of their own (epic 21, 2026-11-22)

**Scope:** what RFC 0004 changed after the review above: a list, not a household, is what is shared, with its own people, catalog and keys. **By:**
Claude Code, with a second model reviewing each step; not independent, **not an audit**.

| Area             | What                                                                                                                                                                                 | Held by                                                                                                     |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------- |
| The leak         | Someone on one list of a group is handed nothing of another: not its rows, items, products, people, links, tombstones or export, nor a way to change it                              | `src/lists/scope.test.ts` (seen to fail with the pull's and apply's checks taken out)                       |
| Operations       | Every list operation names its list and is allowed only to someone on it (its Admin for an Admin's); anyone else reads as not found                                                  | `src/lists/scope.test.ts`, `src/access/routes.ts` and its test                                              |
| The device       | A list taken off a person, or one of two lists of a group, leaves their device with its items and catalog; an item moved, once or twice, to a list they are not on leaves it too     | `src/local/leaving.test.ts` (each seen to fail before)                                                      |
| The catalog      | An add never folds into, or names, another list's product; an item's product is always on its list; a list's products go with it                                                     | `src/lists/scope.test.ts`, `src/lists/adding.test.ts`, `src/sovereign/people.test.ts`                       |
| Links            | A link to a deleted list lets nobody in; deleting a list revokes its links                                                                                                           | `src/lists/scope.test.ts` (seen to fail before)                                                             |
| Keys             | A list's keyring is derived from its group's and opens nothing of another list; a link carries one list's keyring; a value is bound to its list, and one bound to another is refused | `src/keys/household.test.ts`, `link.test.ts`, `src/sync/encrypted.test.ts` (seen to fail without the check) |
| Keys on a device | A move between lists, its Undo, and an edit and a move waiting together are each encrypted for the list the item is on; a change for a list without keys goes to Couldn't sync       | `src/keys/lists.device.test.ts`, `src/keys/transport.test.ts`                                               |
| The move         | Each value for its own row and list; the marker in no table, per list                                                                                                                | `src/keys/server/move.test.ts`                                                                              |

Checked by hand in a browser: a list shared by a link opened for its new person, who could read its items and add one, stored encrypted for that list
alone; the list's maker read it back.

### Findings

7. **Removing someone from a list does not change its keys** (as finding 2, now per list). **Accepted, documented** (`docs/encryption.md`).
8. **The group's keyring is the account's master:** every list's keys are derived from it, so an account's own lists are only as safe as that one
   keyring, which is wrapped under the account's app key and handed to nobody else. **Accepted, as RFC 0004 says.**
9. **A shared list that passes to another person on account deletion stays in the departed account's group,** which nobody owns from then; its new
   Admin holds its keys by their own copy. **Accepted.**
10. **The server still sees who is on which list,** and which list each value is for (`e2.<epoch>.<list>.…`). **Accepted, documented.**
